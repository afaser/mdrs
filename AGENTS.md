# Стиль кода

Rust, только стандартная библиотека. Форматирование — чистый дефолтный rustfmt, собственных конфигов нет (здесь не описывается). Комментариев и doc-комментариев в коде нет — смысл передаётся именами. Документ — обязательная инструкция исполнителю (человеку или агенту): перед правкой читай затронутые разделы, после правки — алгоритм «Ревью»; правило под код не подгоняется.

## Среда

- Окружение — только direnv: пакеты и библиотеки проекта (включая утилиты контейнера и композитора) — в `flake.nix`, переменные — в `.envrc`. Глобальные установки (`nix profile install`, `cargo install`, пакетный менеджер ОС) и `export` вне direnv запрещены; команды — `direnv exec . <команда>`.
- Зависимости — только из crates.io. `vendor/` и `[patch.crates-io]` в репозиторий не возвращаются.
- CPU/IO-bound задачи (`cargo build/check/test/clippy`, `podman build`, генерация, массовые прогоны) — с минимальным приоритетом: `chrt -i 0 nice -n 19 ionice -c 3`. Одновременно — не более одной тяжёлой задачи.
- Параллелизм — не более 10 потоков: `CARGO_BUILD_JOBS=10`, `RUST_TEST_THREADS=10`, `cargo ... -j 10`; лимиты задаются в `.envrc` и не обходятся.
- Контейнеры — только podman, rootless. Приложение — только в контейнере; `cargo run` на хосте запрещён: ни окна в WM пользователя, ни процессов в его сессии.
- Контейнер не получает `DISPLAY`, `WAYLAND_DISPLAY`, X11/Wayland-сокеты и домашний каталог хоста. Дисплей — вложенный headless-композитор внутри контейнера; окно приложения — X11-клиент через rootless Xwayland, ввод подаётся `xdotool` (XTEST), проверка — скриншотом.
- Контейнер получает GPU (`--device /dev/dri`, `--group-add keep-groups`, Vulkan ICD из Nix-окружения), работает без сети и с лимитами `--cpus=10`, `--memory`, `--pids-limit`, `--blkio-weight=10`; `--cap-drop=all`, `--security-opt=no-new-privileges`, `--userns=keep-id`. Без hardware GPU визуальный прогон не выполняется.
- Рендер — только GPU: растеризация, композиция и вывод кадров через wgpu/Vulkan на hardware adapter. Программный рендер, `tiny-skia`, llvmpipe, CPU-растеризация и fallback на software adapter запрещены; software adapter — явная ошибка, а не режим просмотра.
- Запуск — `scripts/sandbox.sh <файл.md>`: собирает бинарь на хосте, запускает его в контейнере под вложенным headless sway и кладёт скриншот в `target/screenshot.png`; `scripts/sandbox-perf.sh [файл.md]` гоняет приёмку прокрутки колесом и drag-выделения с замером CPU.

## Модули

- Подсистема — каталог, точка входа — `mod.rs` внутри него; одноимённый файл рядом с каталогом не создаётся.
- Внутри подсистемы: приватные `mod x;` сверху, ниже блок `pub use`; оба блока в алфавитном порядке.
- Всё, что нужно потребителям, реэкспортится из `mod.rs` подсистемы; наружу не светятся ни промежуточные типы, ни внутренние функции. Промежуточным считается только то, что файл не сделал публичным внутри себя: сокрытие живёт на уровне файла, а не на уровне индекса.
- Новый файл-концепт реэкспортится из `mod.rs` целиком: его публичные типы и публичные операции входят в `pub use`, индекс отражает состав каталога.
- Потребители импортируют только через полный путь крейта, не `super::`. Исключение — модуль тестов: `use super::*;`.

## Файлы

- НЕ смешение ответственностей в одном файле и чужая логика в файле концепта: проверка, которую применяет только один алгоритм, не становится методом постороннего типа. ДА — одна ответственность — один файл; проверки алгоритма живут в том же файле, рядом с единственным вызывом.
- НЕ файлы-корзины (`types.rs`, `geometry.rs`, `utils.rs`) и мега-файлы. ДА — файл на один доменный концепт, названный по главному типу; подсистема — плоский каталог таких файлов, вложенность только между слоями и подсистемами.
- НЕ многопроходный алгоритм целиком в файле его главной функции и набор данных одной фазы в файле чужого концепта. ДА — у каждой фазы, которая прорабатывает собственные данные (коллекцию, индекс, карту), свой файл-концепт со своим типом; фаза без собственных данных — свободная функция в файле того, чей результат она производит; главная функция читается последовательностью имён вызовов фаз.
- Файл не раздувается: реализация без тестов держится в районе сотни строк; устойчивое превышение — признак, что в файл смешаны две ответственности и его надо разделить.
- НЕ разбрасывать операции концепта по файлам. ДА — тип, его конструктор, методы и функции-операции концепта — в одном файле.
- НЕ раздувать файл попутной логикой и не заводить файл для голого вычисления. ДА — отдельный файл получает только концепт: сущность со своими операциями или задача, оформившаяся в тип со своим состоянием; расчёт без собственного концепта идёт в файл того, чей результат он производит, в чужой файл — никогда; родственные мелкие сущности одной темы держатся кластером в одном файле.
- НЕ логика в `mod.rs`/`main.rs` и тесты отдельно от своего кода. ДА — `mod.rs` подсистемы только индекс (приватные `mod` + `pub use`, в алфавитном порядке), `main.rs` — точка входа без логики, `#[cfg(test)]`-модуль внизу файла рядом с тестируемым кодом и локальными хелперами.

## Сущности

Критерии выделения типа — когда обратить внимание:

- собственный инвариант — конструктор его устанавливает;
- собственное поведение — методы, не выразимые примитивом;
- данные ходят вместе — роль требует имени;
- связанные аргументы в сигнатуре — один аргумент-сущность вместо россыпи параметров;
- промежуточное состояние течёт между функциями;
- кортеж или сырой слайс в роли данных.

Ни одного признака нет — значение остаётся локальным `let`, а однородная совокупность — type alias, не новый тип.

Сущность — именованное понятие кода: тип (`struct`/`enum`) или type alias; всё остальное — значение. Имя типа не занято другим типом подсистемы; время жизни экземпляра не критерий (`StringBuilder` создаётся и уничтожается в кадре одной функции — и это нормально).

Вид у сущности ровно один, по инварианту и владению памятью:

| Сущность | Когда заводится | Поля и доступ |
|---|---|---|
| value-тип | инварианта нет, значение передаётся и сравнивается | `pub`-поля |
| тип с инвариантами | конструктор ставит инвариант | приватные поля, доступ через геттеры |
| контейнер | владеет `Vec` | newtype с приватным полем: доступ по ссылке (`-> &[T]`) и consuming-геттер (`self` → `Vec<T>`); вспомогательная логика — приватные функции |
| type alias | однородная совокупность связанных значений | не тип, новое имя понятия |

- НЕ промежуточное состояние, растекающееся между функциями слайсами, индексами или кортежами. ДА — оно собирается в тип: приватные поля, инициализация и инвариант — в конструкторе, наружу — поведение (итератор, методы); межфайловый контракт — конструктор и методы такого типа. Обёртка, не добавляющая ничего, кроме чужого итератора, типом не является.
- НЕ роль в данных без имени (кортеж `.0/.1`, сырой слайс в поле или сигнатуре). ДА — неоформленной сущности дают имя и тип: отрезок — `from`/`to`, не кортеж.
- Принадлежность операции: она живёт у того типа, чьи поля читает в теле; если тело читает только чужие поля и ни разу `self` — это свободная функция файла, который её вызывает, а не метод.
- Арифметика — через std-трейты (`Neg/Add/Sub/Mul/Div`) с `type Output`, приём `self` по значению для `Copy`-типов, конструирование — свободной fn с именем типа. Операции, не выражающие метод, — свободные fn.

## Поток данных

- Данные текут в одну сторону: вход → фазы → результат. Главная функция читается последовательностью имён фаз; назад и вбок данные не текут.
- Фаза — переход «тип входа → тип выхода»: и вход, и выход оформлены сущностями, а не сырыми слайсами, индексами или кортежами; всё, что нужно фазе, лежит в её входе, лишних параметров нет.
- Владение одностороннее: фаза принимает вход по значению и возвращает результат. Запись в чужое состояние по ссылке и захваченное изменяемое — боковой канал; в потоке его нет.
- Между фазами течёт результат, а не внутренности фазы.
- Преобразование чистое: возвращает результат, побочные эффекты — только на границе программы, не внутри фаз.
- Один проход: фаза прорабатывает свои данные один раз.

## Именование

- Функции-конструкторы: свободная fn с именем типа либо метод-конструктор `Type::new`.
- Геттеры без префикса `get_`, по имени поля.
- Имя поля и его геттера — по содержимому: что в поле лежит, — а не по роли, которую значение играет в результате у потребителя.
- Предикаты — глагол; функции-преобразования — по сути того, что делают.
- Тест называется «условие → ожидание»: что дано и что должно получиться.

## Derive-политика

| Категория | derive |
|---|---|
| value-тип, значения сравниваются в тестах | `Debug, Clone, Copy, PartialEq` |
| value-тип, сравнения нет | `Debug, Clone, Copy` |
| контейнер (владеет `Vec`) | `Debug, Clone, PartialEq` |

`PartialEq` — только если тесты сравнивают значения. `Copy` — только если тип не владеет памятью.

## Ошибки и инварианты

- Паника допустима только в тестах; в рабочем коде — `Option`, без `unwrap`/`expect`.
- Конструктор валидирует вход и возвращает `Option<Self>`; сигнатура принимает ровно то, из чего строится инвариант; производные формы конструкторов делегируют в базовый.
- Отказ возвращается ровно на той границе, где он возникает: инвариант, который уже гарантирует конструктор типа, не перепроверяется у потребителей; функция над успешно валидированным типом возвращает готовый результат, а не `Option` под гипотетические будущие отказы.
- Guard конструктора — ранний `return None` с вызовом именованной функции-предиката: проверка инварианта живёт отдельной свободной функцией рядом с единственным вызывом, условие валидации не пишется выражением прямо в `if`.
- Тело функции: guard-early-return → вычисление → сборка результата. `else` не используется.
- Границы нормализуются через `min/max`; вырожденные случаи (обратные, нулевые) отсекаются на входе; допуск сравнения — `f32::EPSILON`.

## Числа

- Единый числовой тип во всём проекте, смешения разрядностей нет; литералы с `.0` (`2.0`, `-1.0`).

## Изменения состояния

- `let mut` только там, где без него не обойтись; логика на выделение/слияние — через итераторы и пересборку в новый `Vec`, не через индексные циклы.

## Реализации (алгоритмы)

- НЕ весь алгоритм в одну функцию (много фаз в теле). ДА — одна фаза одна функция; главная читается последовательностью имён вызываемых шагов.
- НЕ дубль, различающийся только измерением или направлением: два одинаковых прогона, два одинаковых геттера, четыре одинаковых предиката. ДА — различие оформляется значением-измерением (enum): разница живёт в `match` по нему — в методах типа и в одном месте сборки, а тела прогонов остаются одинаковыми: один проход, один итератор, один предикат.
- НЕ вложенные `if`-в-`if` внутри циклов и составные условия в глубине. ДА — guard-выход (`return`/`continue`) наверху, ниже плоские шаги: цикл → цикл → действие.
- НЕ вычисления, спрятанные в условиях и в замыканиях-компараторах. ДА — каждый промежуточный шаг отдельным именованным `let`; сравнение и арифметика — в маленькой именованной функции.
- НЕ `if/else`-выражения и `unwrap`. ДА — ранний `return`/`continue`, `match` по достижимым вариантам, `let … else` для `Option`.
- Поведенческие развилки — только `match` по enum, не bool-флаги.
- НЕ промежуточные представления, которых нет в данных: булевы карты, массивы флагов обхода. ДА — условие проверяется предикатом напрямую по входу; обход — без вспомогательных массивов состояния.
- НЕ своя арифметика там, где примитив уже есть в проекте. ДА — операции трейтов и готовые функции проекта; касты чисел — признак того, что считается не тем типом.
- НЕ индексные циклы и мод-арифметика по краям списка (`for i in 0..n`, `(k + len - 1) % len`). ДА — `windows`, `get`/`match`, явное замыкание списка.
- НЕ механизм, который нельзя объяснить одной фразой (флаги состояния, ручные откаты длины, неявный контракт обхода). ДА — у каждой функции контракт в одно предложение, читаемый по имени и сигнатуре.
- НЕ guard-ветки на состояния, которых невозможно достичь (страховка «на всякий случай»). ДА — только достижимые состояния; накопители — с явным типом (`let mut acc: Vec<T> = Vec::new();`).

## Тесты

- Тест-хелпер — локальная конструкторная функция вместо повторения конструирования с `unwrap()` в каждом тесте.
- Arrange–Act–Assert, пустая строка между фазами.
- Негативный случай фиксируется внутри позитивного сценария явным отрицательным `assert!`, а не отдельным тестом «ничего не произошло».
- Ровно один тест на сценарий приёмки: составные проверки (детерминизм, инварианты результата, замыкание) — утверждениями внутри этого теста, не отдельными тестами.
- Термин результата в имени теста — тот же базовый английский эквивалент термина ТЗ, которым названо свойство в API; синонимы одного понятия не плодятся — один термин на понятие.
- Обязательные границы: пустой вход, вход ровно на границе условия, транзитивные случаи, consuming-операции.

## Ревью

Алгоритм для исполнителя (человека или агента): после каждой правки пройти шаги по порядку; найденный признак правится в коде, правило под код не подгоняется. Каждый шаг оставляет записанный результат — перечисление или ответы на его вопросы; вердикт без них шаг не проходит, «находок нет» допустимо только вместе с этими ответами. Куда смотреть: границы и состав файлов → «Файлы»; тип, поля, сигнатуры, разбиение на сущности → «Сущности»; направление и владение данными → «Поток данных»; форма тела, дубли, состояние → «Реализации (алгоритмы)», «Изменения состояния»; паника, валидация, guard → «Ошибки и инварианты»; имена → «Именование»; тесты → «Тесты».

1. Файлы. По политике раздела «Файлы» пройти каждый изменённый и новый файл: выписать все типы и свободные функции файла и разложить их по темам — по одной фразе на тему; фраза с двумя предметами через «и» — тем две, файл смешивает, разделить; разместить новый код: тип — в файл типа, расчёт без типа — в файл того, чей результат он производит, новый концепт — в новый файл, в `mod.rs` и чужие файлы — никогда; имя файла — по главному типу, не корзина и не мега-файл; новый модуль — в индекс `mod.rs` (приватный `mod` + `pub use`, алфавитно); логики в `mod.rs`/`main.rs` нет, тесты — внизу своего файла. У каждой функции спросить, чьи поля она читает: чужие и ни разу `self` — не метод, место — свободная функция файла-потребителя рядом с единственным вызовом.
2. Сущности. По политике раздела «Сущности» на каждый новый тип ответить: «какие методы ради него пишутся и какой инвариант ставит конструктор?» Нет ни того, ни другого — тип лишний, значение остаётся локальным `let`; поведение есть, инварианта нет — `pub`-поля; инвариант есть — приватные поля и геттеры; владеет `Vec` — контейнер. Роль в данных без имени (кортеж, сырой слайс в поле или сигнатуре) — дать имя и тип; промежуточное состояние, текущее слайсами, индексами или кортежами, — собрать в тип. Имя нового типа сверь с типами подсистемы (`pub struct`, `pub enum`): совпадение с существующим именем — имя чужое, дать понятию своё.
3. Дубль и состояние. Два блока одинаковой формы, различие в одном слове (измерение, направление, ключ) — различие оформить enum-значением, тела оставить одним. У вспомогательного массива, карты или флага спросить: «какое поле данных он отражает?» — ответа нет, он лишний, условие проверять предикатом по входу.
4. Поток. По политике раздела «Поток данных» проверить направление: данные текут в одну сторону (вход → фазы → результат); каждая фаза — переход «тип входа → тип выхода», вход и выход — сущности, а не сырые слайсы, индексы или кортежи; владение одностороннее (по значению → результат), чужого состояния по ссылке и захваченного изменяемого нет; между фазами течёт результат, а не внутренности.
5. Тело. Каждая функция: guard-выход наверху, ниже плоские шаги; каждый промежуточный шаг — именованный `let`; развилка — `match`; сравнение и арифметика — в маленькой именованной функции; составное условие в глубине цикла — поднять guard-ом наверх.
6. Прогон. Компиляция и тесты — по разделу «Среда»; новое поведение — новым тестом на границе (пустой вход, вход на границе условия, транзитивность, consuming); тест-спека ради зелёного прогона не правится.
